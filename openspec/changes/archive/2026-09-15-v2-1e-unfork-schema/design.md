## Context

See proposal.md — Why. Facts of OpenSpec 1.13.0 the design rests on (read in
`dist/core/project-config.js`, `dist/core/archive.js` of the pinned package):

- `config.yaml` has three extension points: `context` (injected into every
  `instructions <artifact>`), `rules.<artifact-id>` (injected into that artifact's
  instructions; a key that matches no artifact of any available schema is a warning), and
  `operations.apply.guidance` / `operations.archive.guidance` (returned by
  `instructions apply` as `operationGuidance`, advisory). This change uses `rules` only.
- The propose skill (`openspec-propose`, generated by `openspec update`, not editable here)
  loops over the schema's artifacts and reports "artifacts ready" once the last one exists;
  it reads `rules` as constraints on the artifact it is writing.
- `openspec archive` moves the change directory whole (`moveDirectory`) and resolves the
  change's schema only for the `skip_specs` marker; an extra file in the directory travels
  with it.
- `openspec status` and `instructions apply` resolve the schema named in the change's
  `.openspec.yaml`; a change whose schema directory disappears stops resolving.

## Goals / Non-Goals

Goals: the same review gate, expressed only in `openspec/config.yaml`; `openspec update` can
bring upstream `spec-driven` changes again; every place that says "artifact" or names the
`architect-review` rule follows.

Non-Goals: changing what the review checks; a deterministic verdict check beyond Group 0's
`grep` (the principle "standard over bespoke checks" holds until a run passes a `rework`);
the PR review (`v2-4`); the pinning strategy for the CLI the carriers run (issue's deferred
scope).

## Decisions

1. **The contract lives in `rules.tasks`, as one more entry.** Rules must be keyed by an
   artifact id; `tasks` is the artifact the review follows, so the planner sees the review
   step and its contract in the same `instructions tasks` call that gives it the delivery
   tasks. Alternatives: `context` — injected into every artifact, the contract would be noise
   in `proposal`/`specs`/`design`; `agent-process.md` — scheduled for deletion (#115), not fed with v2
   content; the subagent file only — Codex would not see it. The entry carries what the
   schema `instruction` and template carried: the three sections, the §I–VII lens, the
   simpler-design, map-gap and `no RED` findings, and the `rework` → apply → re-review loop.
   The former `rules.architect-review` entries merge into it verbatim.
2. **The apply gate is task 0.1 alone.** The issue names `context` for a second statement
   of the gate, and 1.13.0 offers `operations.apply.guidance` for it; both would say what the
   first delivery task already does (`grep -q "^approve"` on the verdict, which the apply
   run reaches before any other task). No apply run exists that a guidance would stop and
   0.1 would not, so neither is added (architect review of this change, finding 3); the
   fork's `apply.instruction` was that second copy and goes with the fork.
3. **The review step is an action of the propose run, not content of `tasks.md`.** The
   `tasks` rule is the last text the propose skill reads, so the entry is worded as what the
   planner does after `tasks.md` is written and before the artifacts are reported ready —
   not as a task group — and names the file it produces. The skill's own loop ends when
   `tasks.md` exists, so this is the one step the schema no longer drives (see Risks).
4. **The subagent reads `openspec/config.yaml` directly.** There is no
   `instructions architect-review` on `spec-driven`. `agents/architect-reviewer.md` step 1
   becomes: read the review entry of `rules.tasks` in `openspec/config.yaml` (contract and
   file structure) and the four artifacts of `openspec/changes/<change>/`; write
   `architect-review.md` there. No `npx` call remains in the file, so `test_pinned_openspec`
   drops it from the pinned set (`test_one_planning_home` keeps it: no `--store`). Alternative:
   `instructions tasks --change <name> --json` and pick the rule out of `rules` — one more
   process for the same text.
5. **This change is planned on `spec-driven` from the start** (`openspec new change
   --schema spec-driven`). Its `architect-review.md` is written by the subagent with the
   contract passed inline — the bridge for one run, since the subagent file changes in this
   PR. A change on `agent-process` would delete its own schema in the middle of the apply
   (`openspec status` would stop resolving it) and could not be resumed.
6. **Archive proof on a fixture, not on this change alone.** This change archives with its
   extra file (the live proof), but the guard has to survive an OpenSpec upgrade — the reason
   for the unfork. `test_review_archives_with_the_change` builds a minimal OpenSpec root in
   `tmp_path` (`openspec/specs/`, one change on `spec-driven` with a proposal, a delta
   adding one requirement, `tasks.md` and `architect-review.md`), runs `openspec archive
   <change> -y` there, and asserts the file is under `openspec/changes/archive/*-<change>/`.
7. **Delete, do not deprecate.** `openspec/schemas/` goes in this PR; `test_forked_schema_validates`
   goes with it. Archived changes keep their `architect-review.md` and their `.openspec.yaml`
   `schema: agent-process` line — the archive is history and no command resolves an archived
   change's schema.

## Risks / Trade-offs

- [`rules.tasks` grows to six entries and is the longest rule] → each entry is one step of
  one run; the review entry is the size of the schema `instruction` it replaces.
- [The propose skill ends its artifact loop at `tasks.md`; the review is now a step in a
  rule the skill treats as a constraint, so a planner can report "artifacts ready" without
  running it and the person approves an unreviewed plan] → the rule names the review as the
  last step before the artifacts are reported ready (Decision 3), and task 0.1 fails
  visibly on the missing file before any delivery task runs; the next propose run is the
  first one that exercises the rule (this change's review ran on the contract passed inline).
- [The fixture test spawns `npx` once more (~10 s)] → same cost class as
  `test_openspec_changes_and_specs_validate_strictly`; cached package.
- [Archived `.openspec.yaml` files still say `schema: agent-process`] → no command reads an
  archived change (`validate --all`, `status`, `list` cover specs and active changes only);
  the Verify group runs `validate --strict --all` after the deletion to show it.

## Migration Plan

One PR. No data migration: the live specs change through the archive of this change; archived
changes are untouched. Rollback is the revert of the PR (the fork returns with it).
